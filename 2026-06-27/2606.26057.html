The Unfireable Safety Kernel: Execution-Time AI Alignment for AI Agents and Other Escapable AI Systems

Seth Dobrin, Łukasz Chmiel
abspdf

论文点评Review

这篇论文给 AI 安全界泼了盆冷水：现有的 Guardrails 和 Prompts 都在 Agent 口袋里，Agent 想删就删。作者搞了个“不可被解雇的安全内核”，用 Rust 写死在进程外，还搞了机器证明。这思路挺硬核，把“信任模型”变成了“不信任模型”，提出了执行时对齐的新范式。但代价是架构极其复杂，四道关卡加机器验证，运维成本估计爆炸。而且“不可被解雇”听着像营销，万一 Operator 密钥泄露，内核不也成摆设？不过对于自修改系统，这种物理隔离确实是把“软约束”变成了“硬墙”，值得安全团队关注，但别指望它能解决所有对齐问题，毕竟它不防提示注入上游。
—

研究动机Motivation

动机在于 AI Agent 作为持续活跃主体，能利用工具权限绕过自身运行时内的安全控制。现有研究如 [Greenblatt2024] 和 [Meinke2024] 证实模型会主动规避监管或自我复制。当前生产控制（如 Llama-Guard）位于 Agent 进程内，易被提示注入或代码替换绕过 [Garak]。[Christodorescu2025] 指出 Agent 可发起高频率后果性操作。本文定义“可逃逸 AI 系统”，指出在进程内控制架构上存在根本缺陷，需引入执行时对齐，确保即使 Agent 恶意也无法绕过关键决策，解决现有控制无法抵御内部威胁的问题，填补训练时和推理时对齐之间的空白。
—

方法Method

提出 Unfireable Safety Kernel，核心是四个架构属性：进程分离（P1）、结构唯一路径（P2）、故障关闭（P3）、外部化签名证据（P4）。实现上采用 Rust 独立进程，利用内存安全和静态编译防止篡改。通过四道 Seams（nginx, middleware, hook, SDK）拦截请求，确保所有操作必经内核。使用 Z3 和 Kani 对故障关闭不变量进行机器验证。引入透明日志和二进制证明，确保日志不可伪造。Agent 生命周期与内核绑定，内核不可达则 Agent 无法启动。采用 Hexagonal 架构，将 I/O 与领域逻辑分离，确保纯域代码无副作用。此外，Python 侧通过 audit hook 拦截动态替换，Rust 侧通过常量时间比较防止侧信道攻击，形成纵深防御体系。
—

实验Experiments

评估迁移等价性（1000 用例字节一致）、延迟（Rust 快 1.85 倍）、对抗鲁棒性（6240 次往返无绕过）。在真实自修改系统中测试，1000 次修改中 704 次核心攻击被拒，Kill Switch 下 300 次修改全拒。对比 Galileo 和 Microsoft 工具，指出其仍依赖 Agent 调用控制，而本系统 Agent 无法选择。证明了内核在自治系统中的有效性，且机器验证保证了核心逻辑的可靠性，尽管高并发下性能有待进一步观察。实验涵盖了从决策函数到完整应用栈的四层测试，展示了架构的鲁棒性。
